## 3. 遇到的问题（按严重度）

### 3.1 键盘焦点丢失（P0）

`Ctrl+Tab` 切换标签后，页面焦点在**文档**而非游戏画布。此时方向键会**滚动网页**而不是移动方块。

证据链：
- 第 4 步后固定区域截图变为纯白（页面滚走了）；
- 分数仍在增长（说明部分按键确实进了游戏）；
- 两者结合说明焦点在"文档/画布"之间发生过切换。

**影响**：这是本轮最主要的不确定性来源，导致第 3、4 步的棋盘读数不可信。

**修正方案**：每轮先用鼠标**点击棋盘中心**确保画布获得焦点，并在按键后校验"棋盘是否变化 + 页面是否滚动"（例如检测滚动条位置或用固定锚点）。

### 3.2 页面级弹窗（P0）

「网络错误，请重新登录」弹窗遮住棋盘，且带「确定」按钮。
**未点击**——这属于"无法确认后果的操作"，按规则停止。

### 3.3 工具链故障（P1）

| 故障 | 原因 | 处置 |
|---|---|---|
| 引擎脚本在 `Invoke-Expression` 下 `New-Object Bitmap` 返回 null | IEX 作用域的变量/类型解析差异 | 放弃文件化引擎，改回内联脚本（已验证可用） |
| 首次裁剪 bbox 高度 977 而非 749 | 上方标题文字被误纳入扫描 | 收紧扫描范围至 y≥420 |
| 9×9 采样点越出格子落到间隙 | 采样半径过大 | 改为 ±3 格 × 15px 步长（居中 90×90 区域） |

### 3.4 颜色辨识的固有风险（P2）

2048 的 `2`(#eee4da) 与 `4`(#ede0c8) 底色非常接近（RGB 差仅 23）。本轮因为使用**众数采样 + 精确匹配**（实测色差 d=0）没有出错，但一旦出现渲染缩放或半透明遮罩，就可能混淆。
**建议**：改用"数字字形模板匹配/OCR"而非纯底色，或至少增加二次校验。

## 4. 事实与推断

**实测事实**
1. `SendInput` 对 Chrome（非提权）可用，4 次方向键全部 `RET=2`。
2. 棋盘像素识别在几何正确时可精确到 `d=0` 的颜色匹配。
3. 第 1 步 2+2 合并为 4，前后帧比对确认。
4. 分数最终为 12，与"两次合并（+4、+8）"一致。
5. 固定区域截图出现纯白 → 页面发生了滚动。
6. 页面出现「网络错误」弹窗。

**推断（未严格证明）**
- 第 2 步与第 4 步的具体棋盘形态（因工具故障/滚动，未取到可信帧）；
- 最大数字为 8（由分数 12 推算，非直接观测）；
- 焦点丢失的确切时刻（只能确定"第 4 步之后"）。

## 5. 是否证明"无需人工的游戏操作"

**部分成立。**

- ✅ 证明：在画面稳定、焦点正确的前提下，Agent 可以完成"截图→识别→决策→按键→复核"的完整闭环，且无需任何人参与（本轮 4 步全是自动）。
- ❌ 未证明：长时间连续自主运行。因为页面级弹窗、焦点丢失这类**与游戏逻辑无关的环境事件**会在数分钟内打断闭环，而当前 Agent 没有"检测异常 → 恢复现场"的策略。

**真正的瓶颈不是 2048 的决策，而是现场维护**：谁保证画布有焦点、页面没滚动、没有遮罩弹窗。
