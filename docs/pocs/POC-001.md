## 4. 已确认的事实 vs 尚未证明的技术假设

### 4.1 已确认事实（实测）

1. 游戏窗口可被稳定截取，1938×1535 原生像素，画面清晰可读。
2. `PrintWindow(PW_RENDERFULLCONTENT)` 对该客户端返回 `FALSE` 且输出纯黑。
3. 游戏存在两个顶层窗口：`MHXYMainFrame`(199834) 与 `XYWZ_CHAT`(460890)。
4. 记事本（同级）上合成点击**真实生效**，坐标 1:1 精确。
5. 游戏前台时 `SetCursorPos` **4/4 失败**；DSH 前台时 **3/3 成功**（同坐标、同进程代码）。
6. `ClipCursor` 为全屏；输入桌面 = 线程桌面 = `Default`。
7. 游戏进程 `mhtab` / `mhmain` 为 **ELEVATED**，Agent 为 **not-elevated**。
8. 合成左键点击：`SendInput=2`、1 ms、无画面变化（3.3%）。
9. 合成 Tab：`down=1 / up=1`、`err=0`、108.83 ms、无画面变化（1.7%）。
10. 手动 Tab 可正常打开地图（**用户报告**，非本 Agent 独立观测）。
11. 地图按钮的语义由游戏自身 tooltip 确认：**「当前地图开关(Tab)」**。

### 4.2 尚未证明的技术假设

| 编号 | 假设 | 置信度 | 缺什么证据 |
|---|---|---|---|
| H1 | 失败主因是 **UIPI 完整性隔离** | 强 | 缺少"提权后成功"的反向对照 |
| H2 | 游戏存在**应用层注入过滤**（低层钩子 / 检查注入标记 / Raw Input 过滤） | 中 | 无法在不提权的条件下探测；且无法解释 `SetCursorPos` 被拒 |
| H3 | 本次 Tab 时光标在窗口外，影响了游戏对键盘的接受 | 低 | 未控制该变量；理论上键盘投递与光标位置无关 |
| H4 | Tab 保持 90 ms 过短，游戏轮询漏采 | 极低（可基本排除） | 90 ms ≫ 60 FPS 单帧 16.7 ms，且低于重复延迟 |
| H5 | 键盘焦点落在子窗口，主窗口前台但未接收 WM_KEYDOWN | 低 | 手动 Tab 在同窗口状态下有效 |

**结论**：H1 是目前**唯一能同时解释"光标被拒"与"键鼠被丢"**的假说；但严格地说，它仍是强推断而非证明。

## 5. 三大技术问题

### 5.1 Windows UIPI（用户界面特权隔离）

**现象**：提权进程的窗口在前台时，中完整性进程的合成输入全部失效。

| 观测 | 说明 |
|---|---|
| 游戏在前台 → `SetCursorPos` 全失败，光标冻结 | **OS 级**拒绝，与坐标无关（移向副屏同样失败） |
| DSH 在前台 → 同 API 全成功 | 差异变量唯一：前台窗口的完整性级别 |
| `SendInput` 返回成功（2 / 1+1） | 事件进入了系统输入队列，**在投递到目标窗口时被丢弃** |
| 手动输入有效 | 游戏本身功能正常 |

**为什么还不能叫"证明"**：
- `SendInput`、`SetCursorPos`、`SendMessage` 走**不同的内核路径**，彼此只能佐证，不能互相替代；
- `WM_NULL` 返回 0、`SetWindowPos` 失败都不足以单独推断 `SendInput` 必然失败（实验中也未把它们当论据）；
- 唯一能建立因果的实验是**反向对照**：同一脚本以管理员身份运行，若成功即证实。该实验需要提权，本轮被明确排除。

**影响**：这决定了"视觉驱动游戏 Agent"在当前权限模型下只能做**只读感知**，不能做**写入控制**。

### 5.2 DPI 坐标系不一致

**观测数据**（同一窗口）：

| API / 视角 | 结果 | 与物理像素比 |
|---|---|---|
| `DwmGetWindowAttribute(EXTENDED_FRAME_BOUNDS)` | `57,74 – 1995,1609` = **1938×1535** | 1:1（物理） |
| `GetWindowRect`（DPI-unaware 进程） | `38,49 – 1330,1072` = **1292×1023** | ×1.5 缩放 |

**同一 `SetCursorPos` 调用在不同进程 DPI 感知状态下的差异**：

| 进程状态 | 调用 | 读回 | 说明 |
|---|---|---|---|
| DPI-aware | `SetCursorPos(3000,1500)` | `3000,1500` | 1:1 物理坐标，可用 |
| DPI-unaware | `SetCursorPos(3000,1500)` | `4500,1079` | 发生 ×1.5 缩放并越界钳制 |
| DPI-unaware | `SetCursorPos(4500,900)` | `6750,1350` | 再次出现 ×1.5 缩放 |

**结论**：本机同时存在三套坐标空间——**截图物理像素 / `GetWindowRect` 逻辑像素 / DWM 物理边界**。任何"截图坐标 → 点击坐标"的换算都必须显式声明处于哪一套空间，并在每次 warp 后**读回校验**。

**工程建议**：把截图、坐标换算、输入合并到**同一个 Per-Monitor-V2 DPI-aware 助手进程**中；只用 DWM 边界做窗口定位；每次 `SetCursorPos` 后必须 `GetCursorPos` 校验 `exact == true` 才允许点击。

### 5.3 DirectX 截图问题

**现象**：`PrintWindow(hwnd, hdc, PW_RENDERFULLCONTENT)` → 返回 `FALSE`，3 ms，输出纯黑（采样色数 = 1）。

**原因**：游戏使用 DirectX 直接呈现，不响应 `WM_PRINT`；GDI 的 `PrintWindow` 拿不到 D3D 表面。

**后果**：
1. 无法**后台/离屏**抓取游戏画面；
2. 必须 `SetForegroundWindow` 抢前台再 `CopyFromScreen`；
3. 抢前台会改变 z-order、遮挡用户界面、并可能引入光标/焦点副作用（本次已实际发生）。

**已验证的替代方案（尚未实施）**：
- **Windows.Graphics.Capture (WGC)**：支持按窗口捕获，可抓被遮挡的 DX 窗口，需 WinRT 互操作；
- **DXGI Desktop Duplication**：抓整个输出，性能高，但仍受遮挡影响；
- 两者都需在 DPI-aware 进程中实现。

按"信息增益 / 操作量"排序，每项都设计为**最小操作**。

| **P5** | **工程化闭环**：单一 DPI-aware 进程 + 坐标读回校验 + 前后帧 diff 阈值 + 操作状态机 | — | 把 POC 变成可复用的 Agent 骨架 | 无 |

### 6.1 若继续推进，建议的下一步（不需要提权、不需要触碰游戏）

1. 先做 **P1 只读探针**（零输入）：确认合成事件是否进入系统输入队列；
2. 再做 **P4 WGC 截图**：把"抢前台"这一步彻底去掉，消除绝大部分副作用；
3. 只有在需要真正"操作"游戏时，才讨论 **P0 / P3** 的权限方案。

### 6.2 目标架构（建议）

```
┌─────────────────────────────┐
│  Agent (LLM, 中完整性)        │
│  视觉理解 / 决策 / 验证       │
└──────────┬──────────────────┘
           │ 结构化指令（非注入）
┌──────────▼──────────────────┐
│  CU-Helper (单一进程)         │
│  · Per-Monitor-V2 DPI-aware  │
│  · WGC 窗口捕获               │
│  · 坐标换算 + 读回校验         │
│  · 输入发送（与目标同权限）     │
│  · 前后帧 diff 判定            │
└─────────────────────────────┘
```

关键设计原则：**感知与执行分离**；执行层必须与目标进程处于同一完整性级别；每一次输入都必须有可验证的回执（截图 diff 或状态查询）。
